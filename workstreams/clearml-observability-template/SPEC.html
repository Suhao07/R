ClearML Observability Template

active-instance

使命

提供可复用的无 GPU Agent ClearML 观测模板，让不同项目只配置责任仓、实验记录、review root、指标映射和 artifact 策略即可把手动训练/评测纳入统一 Web 任务管理。

成功标准

  • profile 可独立校验路径边界、任务类型、指标映射和敏感字段。
  • 已有实验 Markdown、receipt、scorecard 和 review_outputs 可生成不上传的 payload manifest。
  • 责任仓 adapter 只在 rank zero 创建 Task，并能上报配置、指标、artifact、媒体和 Task linkage。
  • 原有手动 SSH/tmux train/eval 命令无需修改即可在结束后显式上报评测结果。

范围

  • ClearML profile/schema、离线 manifest、可选 SDK adapter、手动 post-run eval reporter。
  • loopback Server/SSH tunnel 的配置模板和 artifact 分级策略。
  • SR-Nav 首个 profile 与现有 review_outputs 的兼容导出。
  • 不部署 GPU Agent 或自动启动训练。
  • 不替换 trainer、benchmark、annotation contract、experiment Markdown 或 receipt。
  • 不把大型数据、checkpoint、密钥或私有媒体复制进 ResearchWorkflow。

阶段

  1. P0：冻结旧 Hub，建立 ClearML workstream 和责任边界。
  2. P1：实现 schema、profile、离线校验和 payload manifest。
  3. P2：责任仓 adapter 与不改原 evaluator 的 post-run reporter。
  4. P3：本地 Server、真实 no-GPU eval smoke、结果可视化和证据归档。
  5. P4：训练接入、历史导入和调度能力分阶段评估。

P3 已完成本地 no-GPU Task、结果 artifact 和证据归档；P4 的 UrbanNav 非 DF-OPD Stage-II CFM 训练期诊断 callback、可视化生命周期 manifest/index、显式输入快照、checkpoint URI/下载/parity、双主机 GPFS 可见性、章节媒体报告和本地无 Agent train→eval→report 编排均已实现并有证据。DF-OPD Decision value layout 仅作为历史专项保留。ClearML-native Pipeline、GPU Agent/Queue、完整 test view 和 Stage-I hidden-state 专属信号仍保持明确边界。

持久约束

  • 责任仓拥有实现与实验文档；ResearchWorkflow 只保存小型 schema、policy、profile 和 validator。
  • ClearML Task 是运行索引，不是实验结论的唯一证据。
  • 默认手动启动、rank-zero 写入、唯一 run ID、link-only checkpoint、never-upload raw data。
  • 服务只监听 loopback；真实 Server smoke 前不上传数据或媒体。
